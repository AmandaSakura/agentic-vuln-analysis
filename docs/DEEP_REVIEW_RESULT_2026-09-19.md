## 本轮已经修复

| 问题 | 修复及验证边界 |
| --- | --- |
| 同一候选改了行号，旧证据身份仍相同 | `ValidationSubject` 纳入行号；改变行号、范围、源码或候选都会影响绑定 |
| 探针使用另一份索引执行，却照抄调用者的 subject | 执行前重算实际索引摘要；复现了安全源码 A 被不安全源码 B 的结果错误确认，现已拒绝 |
| 十项验收只检查标签，重复单元或缺少执行证据也可能通过 | 检查固定十个唯一组合、独立冻结标签、完整请求记账；重新验证带正确 subject 的已引用 validator trace |
| 全量入口没有执行十项验收门禁 | 读取最新试跑的原始日志重新验收；核对源码/测试/配置指纹、数据版本、入口方法、模型配置和并发；不信任单独的 `passed=true` |
| 试跑成功后，全量仍可能切回 doGet、旧 thinking 参数或串行执行 | 共用入口选择器和调度器；正式配置与试跑一致，为 doPost、native 模型配置、并发 2；旧实验保留原协议 |
| Ctrl-C 期间已排队任务可能继续启动 | 只提交当前活跃槽位；异常先关闭全局请求准入、取消未开始任务，再等待在途调用退出；SIGINT/SIGTERM 下保留最终汇总 |
| 两个线程首次进入 pytest 门禁发生竞态 | 门禁加进程内锁，同一轮完整测试只执行一次；同时扩大测试子进程凭据环境变量清理范围 |
| 请求记账依赖 case/system/role，重叠或重复记录仍可能混淆 | 每次请求生成唯一 ID，贯穿开始、原始响应、诊断、解析失败和最终结果；按 ID 去重，冲突记为未知；保留旧日志兼容 |
| HTTP 错误中的上报用量丢失，非 JSON 失败未明确记录 | HTTP 状态单独记录；JSON 错误正文仍计入用量；非 JSON/编码失败明确列为无效响应和未知用量 |
| 非文本 content 被强制转成字符串，掩盖协议错误 | 严格要求文本或 null；仍保留失败请求的用量 |
| 已脱敏响应在后续 schema 错误中再次暴露凭据 | 解析使用脱敏后的对象；回归测试确认异常和事件日志均不包含测试凭据 |
| 无关日志文件读取失败，遮住当前请求证据 | 跳过单个不可读或被轮转文件，继续匹配当前请求；冲突仍不作确定性归因 |
| 配置了输出上限，却没有证明代理真的发送 | 诊断记录请求值、上游值和匹配状态；正式准入拒绝把缺失或不匹配的上限当作已验证配置 |
| 实验快照漏掉部分配置和测试 | 源码快照与门禁使用同一份文件清单，包含 src/tests/scripts/configs、依赖锁和契约 |
| 明知验证工具不能给出 CONFIRMED/REFUTED，仍开始以此为目标的付费试验 | 执行验证能力在模型调用前检查；目前 Java 工具不足会直接阻止验证验收试跑，不再耗请求等待不可能出现的证据 |

主要实现位于 `experiment_acceptance.py`、`model_runtime.py`、`live_gate.py`、

### Java 执行验证器缺失

当前 Java 注册工具能支持静态预测，不能提供已执行的漏洞确认/反驳证据。
这是未实现的能力，不是通过调高并发或思考预算能够修复的错误。
现在运行器会在模型调用前报告这一点，不能再把十个标签匹配伪装成完整验证通过。

可审核的实现范围、接口、候选绑定和验收条件见
[Java 验证器实施方案](JAVA_VALIDATION_IMPLEMENTATION_2026-09-19.md)。
该方案仍需实际实现；本轮没有伪造 Java fixture，也没有改变历史结果。
