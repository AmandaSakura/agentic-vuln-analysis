## 实施与验收顺序

1. 完成 K1 的按实际场景生成范围说明，准备明确“尚未执行”，维持现有输入域。跑完整 pytest、harness 和真实快照脚本正反控，提交。
2. 实施唯一允许的 Click callback 适配，使用真实 Click 合成正反控，严格绑定源码、globals、code 和候选 frame；不引入任意包装器展开或内部桩。追加无场景 v6 入口、核实修复调用链，做 3a 脚本容量检查。不能跳过首个无关进程事件。
3. 实现通用紧凑见证投递。删除重复记录，复用已投递候选身份和分类前提；全部准入所需字段必须可用，完整 artifact 和九项核验保留。准备和执行区分，截断或压缩失败不能保留确认资格。目标完整可投递响应 ≤1000 系统观察单位：沿用实际 observation meter 的 UTF-8 字节 token 上界，计入模型可见的完整序列化封装、嵌套 JSON 转义、引用和证明；不改计量算法，不把这项保守预算当成服务端 tokenizer 的实测 token 数。服务端 usage 单独对账。未闭合/失败路径也必须明确报告缺口。
4. 用合成正反控和 hp003/3a 真实脚本，证明在同一 8192 观察预算、原工具步数下可尝试至少两条不同场景，收取各自成本，重复参数仍不重执行。字面量 U 不能 SAFE；缺字段、错身份、伪造或被截断证明仍拒绝。完整 pytest 和 harness 通过，提交后冻结实际运行协议。
5. DeepSeek Flash 四格开发实验：hp003_a/b 和 entry-00390_a/b，每格只启动一次 workflow；允许 workflow 内模型提出多个不同场景。初始输入仍无场景，只有入口/advisory，没有分支值提示。预算固定 8192，工具步数与 M0 E1 相同。总请求 ≤40；累计仍使用原账本，保留已有46请求/281330tokens，累计210请求/250万tokens上限不放宽。全部实际调用通过原模型类和新进程完整门禁，每次原始返回 ID 必须 deepseek-flash。
6. 用户明确要求 E-iter 一定包含 3a，因此保留四格。3a 的真实脚本已发现只读文件系统拒绝 MLflow 临时目录创建，尚未到进程创建边界；将其登记为基础设施受限的探索格，只观察协议和尝试行为，不能据此归因模型场景能力或声明迁移成功。M0 原来的 3a 真实运行仍按其前置条件跳过；E-iter 是另行授权，不反向更改 M0。没有额外源码/prompt修复后重跑机会。固定侧任何 producer CONFIRMED 或已准入最终 VULNERABLE，按 S1 停止；原始拒绝提案另记。
